# Agent Instructions: Reverse-Engineering & Porting

## Non-Negotiable Operational Rules

1. **Emulator Ownership**: Only the human user operates DOSBox / DOSBox-X. Agents NEVER launch, invoke, control, attach to, or inspect live emulator processes. All dynamic reference evidence comes from user-provided capture archives.
2. **Offline Unicorn is Allowed**: Unicorn engine running in offline Python scripts on captured memory files is an authorized validation tool.
3. **No Fake Video / Pre-rendered Frames**: Every intro frame displayed by the player must be computed live by translated JavaScript code. No captured screenshots, screen recordings, or canned image sequences may masquerade as live rendering.
4. **Live Audio Replay**: Sound must be driven by translated original replay/mixer/synthesis/device-control code and original data, with verified device adapters as needed. Web Audio transports output; do not substitute a module-player library or recording.
5. **Fast Assembly Navigation**: Always query the SQLite index (`python tools/asm_index/asm_index.py ...`) instead of dumping large disassembly text listings into agent context.
   Check an existing index's schema and instruction count. If a legacy index omitted addressless IDA instructions, build a new schema-v2 index at an unused path without overwriting the old one. Pass its path explicitly with `--db` for later queries; keep unknown addresses null.
6. **Provenance & Immutability**: Keep original binaries, captures, and existing annotated SQLite indexes immutable.
7. **First Capture Is a Timeline**: Prepare a profile with 1–2-second periodic snapshots, no address stop event, and no instruction tracing. Run `python tools/oracle/validate_capture_profile.py --purpose timeline autocapture-config.json` and show PASS before asking the human to capture. Keep later targeted instruction profiles separate. The human selects the JSON, launches the demo, then starts automatic capture while it runs.
   Plan memory coverage explicitly: the starter region is 8 MiB; justify reductions using bases/limits, available RAM, and required input/heap/stack ranges. Flag out-of-range debugger pointers. Show validator warnings; PASS does not prove RAM coverage. After capture, audit descriptors and asset statuses for actual ranges and partial/unreadable zero-filled bytes. Overlapping selector dumps do not add coverage. Preserve the old session and correct insufficient coverage with a new full-run timeline first; targeted capture is exceptional under rule 13.
8. **Analyst Export Locations**: Save the IDA listing under `oracle/` with a descriptive `.asm` filename. Use code and data dumps already present in `oracle/extract/`; do not ask for another export of a captured data segment. Keep capture sessions immutable and open working copies in IDA. Only separately supplied dumps belong in `oracle/inputs/` with provenance. A selector number is not a proven linear base.
9. **Discover Paths**: Inspect `original/`, `oracle/`, and `oracle/extract/` to find the executable, listing, and relevant session. Read capture manifests to select evidence. Do not ask the human for filenames or session IDs already visible in the workspace.
10. **Real-Input Routine Milestone**: A synthetic-fixture match alone does not complete tutorial Step 06. Compare captured machine code and JavaScript on real demo input from captures or verified original-file bytes, with justified initial state. Document input provenance, compared outputs/registers/flags/memory effects, exclusions, and results. Check required read ranges first; do not silently zero-fill missing dependencies. Resume a mid-routine snapshot at its captured instruction or justify reconstructing entry state. If input is unavailable, inspect workspace evidence or choose another suitable routine before correcting an undersized full-run timeline; use targeted capture only under rule 13. Preserve the timeline profile and capture sessions; leave the milestone incomplete until a real-input comparison passes.
11. **Guarded Pair Trigger Semantics**: `pair_source.offset` is the callee entry after CALL, `previous_offset` is the CALL site, and `pair_return.offset` is the caller continuation after RET. A source on CALL itself will not observe the required four-byte stack push. For E8 rel32 calls, verify captured CALL bytes and show PASS from `validate_capture_profile.py --purpose paired-targeted --call-bytes <verified-call-bytes> <profile>`. Other encodings need explicit review. For an early call, have the human pause at the verified caller CALL, start capture while paused, then resume; the agent never operates DOSBox-X.
12. **Explicit Tutorial Outcome**: Follow `docs/guides/tutorial-outcomes.md` for every step and follow-up. Start with `STEP NN — COMPLETE`, `STEP NN — ACTION NEEDED`, or `STEP NN — INCOMPLETE`, give brief evidence, and finish with `You can continue to Step MM.` only after the whole step and required human review are complete. Otherwise finish with `Stay on Step NN. Next: [You or Agent] — [one concrete action].` Use actual numbers/actions; completed Step 10 ends with `Tutorial complete. You can proceed to your release decision.` Record status in the queue/handoff. Continue available authorized offline work and resume the same step after human captures/reviews; do not require a new prompt or paths. A prepared JSON, synthetic fixture, or inventory alone does not complete Step 06.
    This requirement applies automatically, including to “Resume Step 06” or “The capture is ready”; the human must not repeat reporting rules. After a framework refresh, read the current instructions/protocol and recover the active step from conversation and existing artifacts without restarting completed work.
13. **Full-Run Capture First**: Prefer one start-to-end timeline with the starter 8 MiB memory region at every 1–2-second snapshot. Correct an undersized run with a new broader full-run capture, preserving old sessions, rather than asking for repeated single-point captures. Audit the adequately sized full run and verified originals, and execute bounded intervals offline before escalating. A mid-routine checkpoint may be resumed in Unicorn and compared with JavaScript; live CALL/return pairs and instruction traces are not required for Step 06. Targeted captures are exceptional: the human explicitly requests them, or a specific question demonstrably remains after an adequately sized full run and cannot be resolved offline. Record why the full run cannot answer it; missing bytes from a 1 MiB run do not establish that exception.
14. **Visuals or Sound First**: After Step 07, default to full graphics in Step 08, then sound/synchronization in Step 09; honor sound-first via 07 → 09 → 08 → 10. Track the human's preference and visual/audio completion separately. Deferred sound is pending and does not block graphics. Use a replaceable visual simulation clock based on recovered timing, preserving any music-driven control behavior. Check the full integrated timeline before Step 10. Direct continuation to the unfinished milestone. If adopting older step records (08 sound, 09 graphics), reconcile by artifacts and preserve completed work.
15. **Validation Ladder and Contracts**: Follow `docs/guides/validation-ladder.md`. Compare real-input routines across suitable checkpoints, intervals, whole scenes/endings, inherited transitions, and the actual browser canvas/controls. Use explicit comparison contracts; missing evidence, different initial states, or unsuccessful endpoints never pass. Define observables/exclusions before testing. Triage packed data/loaders and compare indexed routine variants before sharing engines. Keep controlled-schedule correctness distinct from observed timing. Unsupported CPU/FPU/devices need verified offline adapters. Use the tested production adapter contract in `templates/player-template/README.md`; fixtures are not ports, and measured performance/checkpoint sizes are not universal guarantees.
16. **Original Sound Code Only**: Translate and verify the original replay, sequencer, mixer, synthesis, and/or device-control routines and original data. Never substitute a module-player library (including libopenmpt), a generic replacement synth, or recorded music. Do not assume tracker formats, music voice counts, or sound hardware. Web Audio transports output; required device adapters are driven by original code and separately validated. Explicit fixture audio verifies infrastructure only.
17. **Playback Is Not Capture Cadence**: Smooth live playback follows recovered animation/music time. Slow emulator draw completions and screenshot intervals do not set the default player frame rate. Capture-schedule matching is opt-in validation only. Separate timer ticks, draw-dependent state updates, and presentation; a timer frequency does not imply a draw frequency. Preserve feedback/frame-dependent simulation at a justified cadence, independent of refresh/redraw count. Document rates as recovered/measured/provisional, with evidence and verification tasks. A provisional smooth schedule may support visual work but is not verified original timing. Test same-time redraw/cadence independence and transition/audio anchors; do not invent interpolation or new point captures to hide uncertainty. See `docs/guides/sync-and-timing.md`.

## Standard Step 10 release

Follow [the canonical release player standard](docs/guides/release-player-standard.md) and templates/player-template. Keep the canonical landing/player shell, a live module pattern grid driven by the original replay cursor, and measured FPS consistent across ports; adapt metadata/palette/source-specific adapters only. Use exactly one release/ directory, updated in place. Require real pointer/keyboard navigation tests, graphics+audio seek completion, both entry routes, live darkened first-animation landing background, full-run integration and human packaged review. Do not copy another demo's timing, channel count or format. Do not claim a pending harness passed. Framework maintenance itself is not a completed production tutorial step.
